# Техническая подготовка

Шпаргалка под задачи админ-платформы. Эти объяснения описывают общие механизмы; точные версии библиотек и особенности рабочего проекта нужно учитывать отдельно.

## Django и ORM

**Путь запроса.** Уметь объяснить обработку запроса через middleware, URL routing и view, валидацию и проверки доступа, бизнес-логику, обращение к БД и формирование ответа. Если используется DRF — роль serializers, authentication и permissions. Точный порядок хуков зависит от конкретного механизма.

**Ленивый QuerySet.** Конструирование QuerySet часто откладывает выполнение SQL до получения результата. Нужно понимать, какие операции вызывают выполнение, как работает кэш конкретного QuerySet и почему повторный независимый запрос не обязан использовать уже полученные данные.

**N+1.** После получения списка для каждого элемента делается отдельный запрос к связанной сущности. Диагностика — смотреть SQL и число запросов. `select_related` использует JOIN для одиночных связей; `prefetch_related` получает связанные наборы отдельно и сопоставляет их в Python. Выбор зависит от связи и сценария.

**Бизнес-логика.** Объяснить, как в проекте отделены HTTP-представление, правила предметной области и доступ к данным. Не утверждать, что любой проект обязан иметь service/repository слой: важны понятные границы, повторное использование и проверяемость.

**Рефакторинг.** Сначала понять существующий контракт и поведение, зафиксировать критические сценарии проверками, менять небольшими шагами и проверить интеграционные эффекты.

## SQL и транзакции

| Вопрос | Основа ответа |
| --- | --- |
| Зачем индекс | Ускоряет подходящие операции поиска или порядка ценой места и дополнительных затрат на запись |
| Как подобрать составной индекс | Исходить из конкретных фильтров, порядка, распределения данных и плана выполнения |
| Почему индекс не используется | Планировщик может считать другой план дешевле; важны объём выбранных строк, статистика и выражения запроса |
| Что даёт транзакция | Согласованную фиксацию или откат группы изменений в рамках её границ |
| Почему atomic недостаточно | Конкурентный read-modify-write может требовать блокировки, проверки версии или атомарного обновления |
| Когда select_for_update | Когда нужно заблокировать выбранные строки до завершения транзакции |
| Что делать с одновременным редактированием | Проверять версию записи и сообщать о конфликте либо выбирать другую стратегию под требования |
| Можно ли откатить внешний API через rollback | Нет, внешнее действие не входит автоматически в транзакцию БД |

`EXPLAIN` показывает план, `EXPLAIN ANALYZE` выполняет запрос и добавляет реальные показатели. Не путать условную стоимость планировщика с миллисекундами. Seq Scan сам по себе не является ошибкой.

Для миграции обязательного поля в существующей таблице обсудить совместимость старого и нового кода, заполнение существующих строк, ограничения и длительность блокировок. Конкретная безопасная последовательность зависит от БД, объёма данных и версии.

## Asyncio и HTTP

- Event loop переключается между задачами, когда они уступают управление; блокирующий вызов мешает остальным задачам этого потока.
- `async def` не делает синхронный ввод-вывод асинхронным.
- Последовательные `await` не означают конкурентное выполнение.
- `gather` и `TaskGroup` отличаются управлением жизненным циклом и поведением при ошибках. В стандартном случае первая ошибка в `gather` передаётся ожидающему коду, а остальные задачи автоматически не отменяются; TaskGroup при обычной ошибке участника отменяет оставшиеся задачи и ожидает завершения.
- Отмена кооперативна. Ресурсы закрываются через контекстные менеджеры и `finally`; подавление `CancelledError` может нарушать работу структурированной конкурентности.
- Semaphore ограничивает число одновременно выполняющихся операций в своей области. Он не задаёт число запросов в секунду и не становится общим лимитом для всех процессов.
- Пул HTTP-соединений и лимит параллелизма решают связанные, но разные задачи.
- Переиспользование AsyncClient позволяет использовать пул; создавать новый клиент для каждого запроса обычно невыгодно.

HTTPX имеет connect, read, write и pool timeouts. Read timeout ограничивает ожидание порции данных и не является общим временем обработки всего ответа. Для операции с несколькими попытками нужен общий бюджет времени.

## Надёжность внешних интеграций

**Неопределённый результат.** После таймаута операция на стороне партнёра могла выполниться. Повтор запроса на создание сущности может создать дубль.

**Идемпотентность.** Ключ должен распознаваться принимающей стороной или обеспечиваться подходящим протоколом. Просто добавить заголовок в запрос недостаточно. Важно определить, как проверять статус и обрабатывать повтор с тем же ключом и другим содержимым.

**Повторы.** Учитывать семантику операции, тип ошибки, лимит попыток, общий дедлайн, backoff и jitter. Повторы в каждом слое могут умножать нагрузку. Код ответа сам по себе не доказывает безопасность повтора операции с побочным эффектом.

**Изоляция.** Медленный партнёр не должен занимать все общие ресурсы. Обсудить отдельные лимиты конкурентности, ограничение очередей и контроль нагрузки.

| Механизм | Что ограничивает |
| --- | --- |
| Timeout | Длительность ожидания на определённом этапе |
| Общий deadline | Бюджет времени всей операции, включая повторы |
| Rate limiter | Частоту обращений по выбранному ключу |
| Concurrency limit | Число одновременно выполняющихся операций |
| Circuit breaker | Обращения к устойчиво отказывающей зависимости |

## Кэш и доступы

Для кэшируемого ответа определить допустимость кэширования, TTL, инвалидацию и состав ключа. Если ответ зависит от пользователя, организации или прав, ключ и проверки должны предотвращать выдачу чужих данных.

Обсудить массовое истечение популярного ключа и одновременный запрос к партнёру от множества клиентов. Возможные решения выбирать под требования, а не приписывать рабочей системе.

В проверке JWT различать декодирование, проверку подписи и авторизацию действия. Проверять необходимые claims и scopes согласно контракту доверия; ключи получать из доверенного источника. Продумать ротацию, кэш ключей и отказ зависимости.

## Pytest и проверка системы

Повторить fixtures и scope, параметризацию, подготовку и очистку данных, тестирование исключений, подмену сетевых зависимостей и изоляцию состояния.

Unit-тест проверяет локальную логику с ограниченными зависимостями; интеграционный — взаимодействие компонентов; e2e — целевой сценарий через существенную часть системы. Границы определяются проектом, а не только названием теста.

Для изменения конфигурации проверить успешное сохранение, валидацию, права, конфликт версий, историю, отказ внешней зависимости и возможность восстановления. Успешный mock не доказывает совместимость с реальным API: контракт и интеграционные проверки рассматриваются отдельно.

Покрытие показывает исполненные участки кода, но не полноту требований и качество проверок.

## Инфраструктура

Подготовить объяснение реального пути коммита до релиза: проверки, тесты, сборка образа, деплой, проверка результата и откат. Глубину практического участия описывать точно.

Базовые вопросы Kubernetes: назначение Pod, Deployment, Service; readiness и liveness; передача конфигурации; ограничения ресурсов; диагностика незапускающегося приложения; rolling update и откат. Это темы для повторения, а не утверждение о самостоятельном администрировании кластера.

Для брокеров повторить подтверждение обработки, повторную доставку, порядок сообщений, consumer groups и сбои. Зафиксировать, какие именно механизмы были в собственной библиотеке Kafka.

## Практическая задача для репетиции

Спроектировать API управления партнёрами и конфигурациями на Django.

Сначала уточнить пользователей, роли, число партнёров, частоту изменений, чувствительность данных и допустимость задержки применения. Предложить сущности партнёра, конфигурации, версии и записи аудита; объяснить API, пагинацию, фильтры и права.

Затем разобрать два одновременных редактирования, валидацию перед применением, доставку конфигурации шлюзу, откат и недоступность админки. Отдельно обсудить, может ли шлюз использовать последнюю корректную конфигурацию и какие ограничения это накладывает.

Закончить тестами и наблюдаемостью. Не усложнять дизайн очередями и распределёнными протоколами до выяснения требований.
